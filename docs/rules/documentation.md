# 文档治理规则

**Version:** 1.0
**Date:** 2026-06-18
**Status:** Active
**Owner:** agent-plugin maintainers
**Related:** `../../AGENTS.md`, `./change-management.md`

本文是 `agent-plugin` 仓库的长期文档治理规则真源。本文定义文档结构、归档规则、状态语义、命名规范和清理标准；仓库级业务、架构、流程正文仍放在 `docs/` 下。

## 适用范围

本规则适用于仓库根目录、`docs/`、`plugins/*/docs/` 和 `packages/*/docs/` 下的长期文档。

`integration/` 下的外部夹具、示例工程或上游文档不纳入本规则，除非任务明确要求整理对应集成目录。

## 目录职责

### 根目录

- `README.md`：仓库入口，只保留项目概览、常用命令和关键链接。
- `AGENTS.md`：AI agent 执行入口，只引用规则文档并说明执行约束，不复制完整规则细则。

### 根 `docs/`

根 `docs/` 只承载仓库级内容：

- 跨模块架构与边界说明
- 仓库级 ADR
- PR、发布、测试、评审等协作流程
- 跨模块迁移索引和历史路径映射

根 `docs/` 不承载单个插件或包的模块事实、实现细节、接口契约或验证报告；这些内容应下沉到对应模块目录。

### `docs/rules/`

`docs/rules/` 只承载长期治理规范，例如文档、代码、测试和变更治理规则。

`docs/rules/` 不承载项目设计、执行计划、模块事实、需求文档或验证报告，也不设置 `README.md` 作为额外入口。

### `plugins/*/docs/`

插件文档只描述对应插件的长期事实：

- 插件需求、产品范围和验收标准
- 插件架构、设计、协议/配置契约
- 插件测试策略、验证报告、发布和排障手册
- 插件内文档迁移映射

### `packages/*/docs/`

包文档只描述对应共享包的长期事实：

- 包职责、架构边界和 public contract
- 包内设计方案、接口约束和兼容策略
- 包级测试策略、验证证据和发布注意事项

## 标准分类

以下目录是长期文档分类白名单。目录按需创建，不要求每个模块预创建完整空目录树。

| 目录 | 作用 |
|---|---|
| `product/` | 需求范围、验收标准、非功能要求，回答“做什么” |
| `architecture/` | 架构原则、模块边界、数据流、状态模型，回答“为什么这样设计” |
| `architecture/adr/` | 架构决策记录，一条长期决策一篇文档 |
| `design/` | 实施方案、模块拆分、兼容策略，回答“怎么做” |
| `design/interfaces/` | API、协议、配置、SPI 等接口契约 |
| `quality/` | 测试策略、验证报告、追踪矩阵，回答“如何证明可交付” |
| `operations/` | 发布、排障、日志、维护和回滚手册 |
| `migration/` | 旧路径到新路径映射、废弃说明和迁移记录 |

根 `docs/` 可以使用其中适合仓库级内容的目录，例如 `architecture/`、`adr/`、`operations/`、`testing/`、`migration/`；模块目录优先使用完整分类。

## 状态与事实源

长期文档必须通过 `Status` 表达事实源语义：

| 状态 | 语义 | 使用规则 |
|---|---|---|
| `Active` | 当前事实源 | 可作为实现、测试、发布和评审依据 |
| `Draft` | 未冻结草案 | 只能作为讨论输入，不能作为最终实现依据 |
| `Deprecated` | 已废弃 | 必须指向替代文档、迁移路径或删除计划 |
| `Historical` | 历史记录 | 只用于追溯，不参与当前实现决策 |

同一主题不得存在多个 `Active` 真源。若需要拆分，必须明确主文档与补充文档的关系；若需要替换，必须先把旧文档标记为 `Deprecated` 或 `Historical`，并修正引用。

## 元数据规范

长期文档顶部应包含以下元数据：

- `Version`
- `Date`
- `Status`
- `Owner`
- `Related`

`README.md`、`AGENTS.md`、轻量入口文件和迁移映射表可豁免完整元数据，但必须保持职责清晰，并能通过正文或路径判断其作用域。

元数据规则：

1. `Version` 表示文档版本，不表示产品或包版本。
2. `Date` 使用最后一次语义更新日期。
3. `Status` 必须使用本文定义的状态之一。
4. `Owner` 使用维护者角色，不写个人临时归属。
5. `Related` 只列直接相关的 active 文档或必要历史依据，避免堆砌链接。

## 命名规范

1. active 文档文件名使用小写 `kebab-case`。
2. 日期前缀只允许用于历史计划、迁移记录、归档记录，不用于 active 事实源。
3. 避免把 `v1`、`v2`、`final`、`new`、`old`、`latest` 等版本或状态词写入文件名；版本和状态写入元数据。
4. 同一目录下文件名应表达文档主题，不表达实现阶段。
5. 目录入口文件可使用 `README.md`；AI 执行约束文件可使用 `AGENTS.md`。

## 生命周期归档规则

一个需求从提出到上线，文档应按长期责任归档，而不是按阶段堆放：

1. 需求范围、验收标准和非目标进入 `product/`。
2. 长期架构边界和关键决策进入 `architecture/` 或 `architecture/adr/`。
3. 实现方案进入 `design/`；协议、配置、API、SPI 进入 `design/interfaces/`。
4. 测试策略、验证结果和追踪矩阵进入 `quality/`。
5. 发布、排障、日志、回滚和维护说明进入 `operations/`。
6. 路径迁移、废弃说明和历史兼容记录进入 `migration/`。

代码是真实实现来源。文档应记录长期边界、契约、决策和可维护知识，不复制代码细节。

## 一次性计划退场

一次性实施计划、临时调研记录和阶段任务清单不应长期作为 active 文档主入口。

需求完成后必须选择一种处理方式：

1. 删除一次性计划。
2. 将仍有长期价值的结论沉淀到 `product/`、`architecture/`、`design/`、`quality/` 或 `operations/`。
3. 如为历史迁移依据，转入 `migration/` 并明确状态为历史记录。

不得让已完成计划与长期事实文档并列成为双真源。

## 新增文档判定

新增文档前必须先判断其长期归属：

1. 是否属于仓库级、插件级、包级、流程级或治理级内容。
2. 是否已有 active 文档可承载该内容。
3. 是否需要成为长期事实源，还是只应进入 issue、PR 描述或临时计划。
4. 是否需要同步更新入口、模块级 `AGENTS.md` 或迁移映射。

若文档只服务一次性实施，不应默认创建 active 文档；应优先沉淀到现有设计、质量或运维文档中。

## 老旧文档清理

满足以下条件之一的文档应迁移后删除，或直接删除并登记原因：

1. 内容已被模块目录中的 active 文档取代。
2. 只描述已完成的一次性任务，且没有长期维护价值。
3. 引用旧路径、旧术语或旧架构，继续保留会误导开发。
4. 与当前代码、协议或发布流程不一致，且不应作为历史依据保留。

删除或迁移文档时必须：

1. 更新受影响引用，避免新增断链。
2. 在对应 `migration/` 文档中登记旧路径、新路径或删除原因。
3. 保持根 `docs/` 只承载仓库级内容，模块事实下沉到对应 `plugins/*/docs/` 或 `packages/*/docs/`。

迁移文档时还必须确认新路径的状态、元数据和命名符合本文规则；不能只移动文件路径而保留旧语义。

## 引用规则

1. 新增引用优先指向 active 文档，不指向历史计划或过期草稿。
2. 模块内部引用优先使用模块内相对路径。
3. 跨模块引用必须说明引用目的，避免用另一个模块文档替代本模块事实源。
4. 发生路径迁移时，同步修复受影响链接并更新迁移映射。

## 验证清单

新增、迁移、删除或大幅更新文档时，至少检查：

- 路径是否符合目录职责和文档类型路由。
- `Status` 是否允许该文档作为事实源。
- 元数据是否完整，命名是否符合规则。
- 是否引入旧路径、断链或多个 active 真源。
- 是否需要更新模块级 `AGENTS.md`、入口文档或迁移映射。
- 纯文档规则改动是否只影响文档范围，未混入代码或无关工作区改动。

## 规则优先级

1. 更深层目录的 `AGENTS.md` 可定义更严格的局部规则。
2. 局部规则与本文冲突时，在其作用域内以更深层规则为准。
3. 局部规则不应复制本文全文，只记录差异、补充约束和本目录入口。
